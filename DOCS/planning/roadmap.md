## 마일스톤 1 — 게임 루프 뼈대

목표: 폰 브라우저 3개와 스크린 1개로 입장 → 문제 → 답변 → 마감 → 정답 공개 → 대기실/퇴장 → 패자부활전(복귀/탈락) → 다음 문제 → 종료가 끝까지 돌아간다. 아바타는 이름표 달린 원으로 대체.

- [ ] 모노레포 초기화 (`server/`, `web/`, `shared/`), TypeScript·ESLint·Vitest
- [ ] `shared/` 이벤트 타입과 zod 스키마 → [[realtime-protocol]]
- [ ] 엔진: 방·참가자 상태 머신, 라운드 모드(NORMAL/REVIVAL), 답변 자격, 판정, 스트라이크, 되돌리기 → [[game-flow]]
  - [ ] 순수 함수 단위 테스트: 마감 유예, 미응답=오답, 2스트라이크, undoReveal 복원
  - [ ] 이동 숨김 모드 테스트: `liveMovesUntilOrderNo` 이후 문제에서 스크린 룸에 `choice`가 마감 전 절대 나가지 않음
  - [ ] 패자부활전 테스트: 대기실만 답 가능, 정답→복귀(스트라이크 유지), 오답·미응답→탈락, 부활자 다음 오답→즉시 탈락, 대기실 0명 시작 거절, 부활 라운드 undo
- [ ] Fastify + Socket.IO 게이트웨이, 역할별 룸, 세션 토큰 인증
- [ ] SQLite 스키마·스냅샷·기동 복구 → [[data-model]]
- [ ] 참가자 화면: 입장 폼(검증·동의), 로비, O/X, 관전(대기실·패자부활전 중 생존자), 패자부활전 답변, 결과, 탈락
- [ ] 사회자 콘솔: PIN 로그인, 문제 JSON 붙여넣기, "다음 단계" 버튼, "패자부활전 시작" 버튼, 참가자 목록
- [ ] 스크린: 상태별 레이아웃, 구역, 이름표 원형 아바타(DOM), 타이머
- [ ] 서버 시각 동기화(`time:ping`) 훅

산출물: [[architecture]], [[game-flow]], [[realtime-protocol]], [[data-model]]

## 마일스톤 2 — 라이브 무대 연출

목표: 스크린에서 아바타가 돌아다니고 O/X로 걸어가며, 마감·정답·탈락 연출과 효과음이 나온다. 가상 참가자 100명 부하에서 30fps 이상.

- [ ] DOM 무대(React 컴포넌트 + CSS transform/transition): 구역 격자 슬롯, 아바타 컴포넌트, 이름표
- [ ] 이동 숨김 모드: 상단 자막, ✓ 배지, 마감 시 일제 이동
- [ ] 유휴 배회·구역 이동·도착 후 배회 애니메이션
- [ ] 조합형 아바타 파츠 제작(SVG → 스프라이트시트)과 폼 미리보기·재추첨
- [ ] 마감 카운트업, 정답 구역 강조·색종이, 대기실 이동, 탈락 연기 연출
- [ ] 패자부활전 무대 교대 연출(생존자 하단 이동 ↔ 대기실 무대 진입, 2초 고정), "부활!" 꼬리표, 다음 라운드 복귀 연출
- [ ] 효과음 5종과 "사운드 켜기" 버튼
- [ ] 연결 끊김 반투명 표시, `room:state` 복구 시 즉시 배치
- [ ] 가상 참가자 시뮬레이터(스크립트로 N명 접속·랜덤 답변) → 렌더링·서버 부하 측정

산출물: [[screens]]

## 마일스톤 3 — 운영 기능

목표: 사회자가 개발자 없이 준비·진행·정리를 끝낼 수 있다.

- [ ] QR 코드 생성(스크린 로비 + 콘솔 인쇄용)
- [ ] 문제 CSV/JSON 업로드·검증·인라인 편집·순서 변경, 이미지 첨부, 패자부활전용(`kind`) 표시
- [ ] 타이머 연장·조기 마감, 판정 취소, 라운드 취소, 참가자 복구·퇴장
- [ ] 패자부활전 예정 시점 설정(`revivalAfterOrderNo`)과 "다음 단계" 버튼 자동 전환, 추가 부활전 `force` 확인
- [ ] 참가자 CSV 내보내기, 전화번호 마스킹, 전화번호 일괄 삭제·자동 파기
- [ ] 콘솔 로그인 실패 잠금, 요청 본문 로깅 금지 확인
- [ ] 생존자 0명·1명 경고, 종료 화면
- [ ] 종료 화면 우승자 지정 버튼과 왕관 연출(오프라인 결승 뒤)
- [ ] 운영 매뉴얼 1장(콘솔 버튼 순서, 사고 대응) → `DOCS/planning/runbook.md`

## 마일스톤 4 — 배포와 리허설

목표: 공개 URL에서 실제 폰 10대 이상으로 일반 5문제 + 패자부활전 1회 리허설 성공. → [[ADR-0004-cloud-deploy]]

- [ ] Dockerfile, Cloud Run 배포(인스턴스 1 고정, CPU 상시, 타임아웃 3600, 세션 어피니티)
- [ ] SQLite → GCS 스냅샷 복사와 기동 시 복원
- [ ] 핫스팟 리허설: 노트북을 휴대폰 핫스팟에 물리고 콘솔 + 스크린 창 동시 동작 확인, 백업 핫스팟 폰 준비, 테더링 데이터 한도 확인
- [ ] 부하 테스트: 가상 100명 동시 답변, 재접속 폭주(전원 끊고 붙이기), 핫스팟 끊고 다시 붙였을 때 콘솔·스크린 복구
- [ ] 리허설 1차(개발 중 폰 3~5대), 2차(행사 규모 축소판 10대 이상, 실제 프로젝터)
- [ ] iOS Safari·Android Chrome 실기기 확인: 진동, Wake Lock, 100vh, 백그라운드 복귀

## 마일스톤 5 — 본행사

목표: 사고 없이 진행하고 개인정보를 파기한다.

- [ ] 행사 전날 배포 동결, 문제 최종 업로드, 콘솔·스크린 사전 접속
- [ ] 당일: 핫스팟 연결·백업 폰 확인 → 스크린 창을 프로젝터로(콘솔 창은 노트북에만) → 전체화면·사운드 켜기 → QR 노출 → 입장 마감 → 진행 → 종료 후 오프라인 결승 → 우승자 지정
- [ ] 종료 후: 생존자 CSV 저장 → 경품 연락 → 전화번호 삭제 → GCS 스냅샷 삭제 → 인스턴스 0으로 내림

## 의존 관계

> [!note] 순서 제약
> - M1의 엔진과 프로토콜이 확정되어야 M2 스크린 연출을 시작할 수 있다(이벤트 페이로드에 의존). 단, 아바타 파츠 제작은 M1과 병행 가능.
> - 인원이 50명으로 확정되어 M2 렌더링은 DOM, M4 부하 테스트는 100명 기준이다. 인원이 200명을 넘게 바뀌면 렌더링 방식을 다시 검토한다.
> - M4 리허설은 실제 프로젝터와 행사장 네트워크 답사 후에 해야 의미가 있다.
