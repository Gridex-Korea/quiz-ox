# ADR-0002 게임 상태는 단일 서버 인메모리 + SQLite 스냅샷으로 관리한다

## 맥락

한 번에 한 게임만 돌고, 참가자는 최대 수백 명이다. 마감 판정·스트라이크 계산은 단일 시각 기준으로 원자적으로 일어나야 하며, 정답 공개를 되돌릴 수 있어야 한다. 반면 서버가 죽으면 행사가 멈추므로 재시작 후 마지막 상태로 돌아올 수 있어야 한다. 개발·운영 인력은 한 명이다.

## 결정

게임 상태의 진실은 **서버 프로세스 1개의 인메모리 객체**다. 모든 명령은 이 객체 위에서 동기적으로 처리되어 경쟁 조건이 없다. 상태 전이마다 **SQLite(better-sqlite3) 파일**에 트랜잭션으로 기록하고, 기동 시 이를 읽어 복구한다. 서버 인스턴스는 항상 정확히 1개만 띄운다.

## 검토한 대안

| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| Redis를 상태 저장소 + Socket.IO 어댑터로 두고 다중 인스턴스 | 수평 확장, 인스턴스 장애 허용 | 인프라 1개 추가, 마감 판정을 분산 락 또는 Lua로 원자화해야 함, 비용 | 참가자 500명은 Node 1개로 충분. 복잡도가 이득보다 큼 |
| PostgreSQL을 진실로 두고 매 답변을 DB에 기록 | 표준적, 조회 자유 | 답변마다 왕복 지연, 500명 동시 답변 시 잠금 경합, DB 인스턴스 비용 | 인메모리보다 느리기만 하고 얻는 것이 없음 |
| 인메모리만 (영속화 없음) | 가장 단순 | 서버 재시작 = 게임 초기화, 참가자 재입장 불가(입장 마감 규칙과 충돌) | 행사 중 크래시 한 번이 치명적 |
| JSON 파일 스냅샷 | 의존성 0 | 부분 쓰기 시 파일 깨짐, 쿼리 불가 | SQLite가 같은 노력으로 트랜잭션과 무결성을 줌 |

## 결과

- 좋아지는 것: 엔진을 순수 함수 + 동기 코드로 짤 수 있어 단위 테스트가 쉽고, 마감 판정에 락이 필요 없다. 되돌리기는 스냅샷 한 줄 저장으로 끝난다([[data-model]]의 `round_results.snapshot_before`).
- 감수하는 것: **인스턴스를 하나만** 띄워야 한다. 배포 환경에서 자동 확장·스케일 투 제로를 명시적으로 막아야 한다([[ADR-0004-cloud-deploy]]). 재시작 사이의 몇 초는 서비스가 끊긴다(Socket.IO 재접속으로 복구). 동시 행사 2개는 지원하지 않는다.
