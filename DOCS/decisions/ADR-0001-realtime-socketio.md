# ADR-0001 실시간 통신은 Socket.IO(WebSocket)로 한다

## 맥락

참가자 수백 명의 O/X 선택이 0.5초 안에 스크린 아바타 이동으로 보여야 하고, 타이머·정답 공개가 모든 화면에 동시에 도착해야 한다. 참가자 폰은 이동통신 데이터 위에서 화면이 잠기고 브라우저가 백그라운드로 가며 연결이 자주 끊긴다. 재접속과 상태 복구가 프로토콜 수준에서 쉬워야 한다.

## 결정

서버-클라이언트 실시간 통신은 **Socket.IO**(WebSocket 전송, 필요 시 HTTP 롱폴링 폴백)로 한다. 세 역할을 Socket.IO 룸(`players`, `screen`, `host`)으로 나누고, 참가자 개별 전송은 `p:<playerId>` 룸으로 한다. 입장 등록과 파일 업로드처럼 요청-응답형 작업만 HTTP로 둔다.

## 검토한 대안

| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| 순수 `ws` 라이브러리 | 가장 가볍고 의존성 적음 | 룸, 재접속, 확인 응답, 하트비트를 직접 구현 | 인력 1명에 재접속 로직을 직접 짜는 것은 행사 당일 리스크 |
| Supabase Realtime / Firebase RTDB | 서버 코드 없이 브로드캐스트 | 마감 판정·스트라이크 계산 같은 **서버 권한 로직**을 둘 곳이 애매함(Edge Function 지연), 외부 서비스 장애에 행사가 묶임 | 판정은 반드시 서버가 단일 시각 기준으로 해야 함 |
| Server-Sent Events + HTTP POST | 단순, 방화벽 친화 | 단방향이라 답변은 별도 POST, 연결 수 제한(HTTP/1.1 브라우저당 6개) | 폰에서 두 채널 관리가 오히려 복잡 |
| 짧은 주기 폴링 | 구현 가장 쉬움 | 500명 × 1초 폴링 = 초당 500 요청, 아바타 이동이 끊겨 보임 | "라이브로 이동하는 모습"이라는 핵심 연출을 만족 못 함 |
| WebRTC 데이터채널 | 저지연 | P2P 토폴로지가 이 문제에 맞지 않음(전원이 서버와만 통신) | 과잉 |

## 결과

- 좋아지는 것: 자동 재접속·룸·ack가 내장되어 [[game-flow]]의 재접속 흐름이 짧아진다. 브라우저 호환성 걱정이 없다.
- 감수하는 것: 순수 WebSocket보다 프레임 오버헤드가 조금 있다(페이로드가 작아 무시할 수준). 서버를 수평 확장하려면 Redis 어댑터가 필요하지만 [[ADR-0002-single-instance-state]]에 따라 단일 인스턴스로 가므로 해당 없음.
